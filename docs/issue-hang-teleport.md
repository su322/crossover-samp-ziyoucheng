# 传送后卡死（2026-11-08）

> 返回 [README](../README.md)

0.3.DL-R1 下反复出现的卡死，本轮抓到了一次比较完整的现场，把范围缩小到「流式加载」这一层。

---

## 现象

- **传送到某个地点后卡死**（本次是服务器传送功能，目的地附近有自定义地图）
- **卡死间隔不固定**，有时几十分钟，有时更久
- **卡死时声音还在播**（引擎声、循环音效继续）
- 进程存活，画面冻结，日志停止增长
- 系统里**零崩溃报告**，`~/Library/Logs/CrossOver/` 为空

---

## 三个观察点指向同一结论

| 观察 | 推论 |
|---|---|
| 声音还在 | 音频线程独立存活 → **不是整个进程冻死**，是渲染/主线程被阻塞 |
| 传送后触发 | 玩家位置瞬间跳远 → streaming 要卸载旧区、加载新区 |
| 间隔不固定 | 取决于传送目的地有多少模型需要现加载 |

**结论：渲染线程卡在模型加载/上传上，不是死机，也不是网络问题。**

传送时如果目的地有大量自定义模型（这台服务器有 **559 个** .dff/.txd），渲染线程要同步地：读文件 → 解码 → 上传 GPU。d3dmetal 在这一步阻塞。

| 目录 | 文件数 | 大小 | 最后写入 |
|---|---|---|---|
| `154.12.58.112.7777` | 559 | 167 MB | 2026-11-07 17:53（全部重写）|
| `45.158.21.28.7777` | 559 | 167 MB | 2026-11-05 14:07 |
| `114.132.198.92.7777` | 270 | 202 MB | 2026-11-05 13:50（另一个服）|

**本次卡死时（11-08）零新写入**，说明模型早就缓存好了，卡在本地加载而不是网络。

### 一个长期隐患：节点轮询导致重复下载

`USERDATA.DAT` 里收藏的是**域名 `ds.zycdjz1.com`**，这个域名有 4 条 A 记录轮询。0.3.DL 的缓存目录是**按 IP 分**的，所以：

```
11-05 连到 45.158.21.28   → 下载 559 个文件 / 167 MB
11-07 连到 154.12.58.112  → 又下载 559 个文件 / 167 MB
```

每换一次节点就重下 167 MB。**建议收藏改用固定 IP `154.12.58.112:7777`**（见 [附录 J](issue-player-count.md) 同样的建议）。

## `stream.ini` 的单位是 KB（反汇编证据）

`stream.ini` 的 `memory` / `devkit_memory` 长期没有官方说明。直接反汇编 `gta_sa.exe` 的解析代码：

字符串表（`0x0086A8B0` 起）：

```
0x0086A8B0  "devkit_memory"
0x0086A8C0  "memory"
0x0086A8C8  " ,\t"          ← 行内分隔符
0x0086A8CC  "stream.ini"
```

解析函数在 `0x005BCD44`：

```asm
5bcd44:  pushl  %edi
5bcd45:  calll  0x82258e        ; 把数字解析成整数
5bcd4a:  addl   $0x4, %esp
5bcd4d:  shll   $0xa, %eax      ; eax <<= 10  →  ×1024
5bcd50:  movl   %eax, 0x8a5a80  ; 存进全局变量
```

`shll $0xa` 就是左移 10 位 = **乘 1024**。所以单位是 **KB**：

| 值 | 实际 |
|---|---|
| 13500（原版） | 13.2 MB |
| 30000 | 29.3 MB |
| 200000（当前） | 195.3 MB |

### 坑：两个参数写同一个变量

```asm
5bcd4d:  shll $0xa, %eax        ; memory 的值
5bcd50:  movl %eax, 0x8a5a80    ; 存
...
5bcd75:  shll $0xa, %eax        ; devkit_memory 的值
5bcd78:  movl %eax, 0x8a5a80    ; 存到同一地址 → 覆盖前一个
5bcd7d:  movb $0x1, %bl         ; 置标志位
```

**`devkit_memory` 在后面执行，会覆盖 `memory`。** 只改 `memory` 不改 `devkit_memory` 等于白改。

## 真正的上限：2 GB 地址空间

```
gta_sa.exe    PE32    LARGE_ADDRESS_AWARE = NO
samp.exe      PE32    LARGE_ADDRESS_AWARE = NO
```

32 位进程且未开启大地址，用户态只有 **2 GB**。内存账本（195 MB 池子时）：

| 占用方 | 估算 |
|---|---|
| 模型数据池 | 195 MB |
| 纹理池 | 100–200 MB |
| 主程序 + 代码 + 全局数据 | 150–250 MB |
| 音频（bass.dll 等） | ~50 MB |
| Wine 自身映射 | 100–200 MB |
| **合计** | **~700–850 MB** |

还有 1 GB 余量。而且这是**上限不是预分配**：`ms_memoryAvailable` 只是计数器，按需填充。

想再往上必须突破 2 GB：

1. `WINE_LARGE_ADDRESS_AWARE=1` 环境变量（需改走脚本启动，双击传不进去）
2. 改 PE 头 `Characteristics` 的 `0x20` 位打 4 GB patch（动 `gta_sa.exe`，有 `.orig` 备份）

## 已做的调整（2026-11-08）

| 文件 | 改动 | 备份 |
|---|---|---|
| `sa-mp.cfg` | `fpslimit 90 → 60`、`audioproxyoff 0 → 1` | `sa-mp.cfg.bak-20261108-185520` |
| `stream.ini` | `memory` / `devkit_memory` `13500 → 200000` | `stream.ini.bak-20261108-185753` |

理由：
- `fpslimit` 降到 60 砍掉 1/3 的 x86→ARM64 翻译负载
- `audioproxyoff=1` 关掉音频代理（历次静默退出都发生在 `Audio stream:` 之后，见[附录 G](issue-silent-exit.md)）
- `stream.ini` 加大模型常驻池，减少传送时「卸载→重读」的往返

---

## 一个必须说清楚的前提

**池子大 ≠ 不卡。** 它只解决「去过又离开的地方，回来时不用重读」。如果传送目的地是**从来没去过**的，模型还是要现读、现解码、现上传，该卡还是卡。

真正能压住传送卡死的是**降低绘制距离**（`Options → Display Setup → Draw Distance`），因为它直接减少「一次要加载多少个模型」。
